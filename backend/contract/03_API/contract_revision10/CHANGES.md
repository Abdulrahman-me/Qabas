# Contract revision 10 candidate: changes from revision 9

**Status:** candidate prepared during the final engineering review (2026-10-03). It needs engineer approval under [O-01](../../00_REVIEW/STATUS_AND_OPEN_DECISIONS.md). **Base:** the received reply8 revision 9 candidate (`10_REFERENCE/engineer_delivery/reply8/contract_revision9`, schema SHA-256 `e38f032c38ff5d02de549205680e50a3f7691e1dd5cc87138b0fe4af2c24d4f3`), which stays unchanged for audit.

Revision 9's custom export left about 25 documented request and response shapes as generic JSON objects: learner `SessionResult` XP/streak/review items, stats, reviewer runs/drafts/QA, metrics, conversation history and async duel answers. Several endpoint bodies had no exported root at all (`PATCH /me` had no model; client socket messages were prose only). Dart or OpenAPI clients generated from it would therefore have hand-written or `Map<String, dynamic>` code exactly where the teams most need to agree. Gate approvals also could not prove which artifact a reviewer approved.

## Migration implications

- **Production data:** none. No revision 9 service or database was deployed. If one exists, migrate rows by adding `review_digest`/`published` to stored factory runs (`published` from `published_lesson_id`, digest recomputed while at a gate). No learner snapshot changes, because learner shapes are wire-identical.
- **Pinned sessions:** unaffected. Session, Exercise, AnswerEvaluation and SessionResult JSON are byte-compatible.
- **Curriculum amendment (class F):** no data is deployed. If any existed: backfill `users.goal_anchor = null`; derive journey states from prerequisites instead of stored sequential locks (`learner_units` keeps only test/pretest facts); store each published lesson's approved plan fields (prerequisites, introduced concepts, standalone flag; a legacy lesson without a plan is treated as having no prerequisites and not standalone-eligible until re-reviewed); set `sentences.role` (`claim` where claim IDs exist, otherwise `framing` for former `connective` sentences) and `claims.basis = source`; unpublished runs at a gate are re-planned or re-drafted, since their digest-bound artifacts lack the new fields.
- **Clients:** regenerate DTOs from this schema. The reviewer console must echo `review_digest`; learner clients must send the §3.2 identity headers, use `Duel.ws_url` verbatim, and send `Idempotency-Key` where required.
- **Mocks:** the mock factory-run fixtures gain `review_digest`/`published`; mock repositories compute digests with `review.py` semantics (or any stable value; the mock only has to require an echo).
- **Fixture generators:** `make_fixtures.py`/`extend_fixtures.py` do not produce reviewer runs; reviewer examples live in the API requirements and are validated from there. For class F they now generate the test curriculum with an Explorer-only first unit (its ten New Muslim lesson/assessment variants are no longer produced: 392 → 382 fixtures), prerequisite Soft Locks and standalone lessons. Run them in UTF-8 mode (`PYTHONUTF8=1`); on Windows normalize line endings to LF and path separators to `/` afterwards, as the received files use.
